# Исполнение спецификации по готовому фронту

План задаёт граф зависимостей. Готовый фронт состоит из частей, у которых приняты все блокирующие зависимости. Цель: реализовать весь согласованный результат, сохраняя единое состояние интеграции и доказательства приёмки.

## Контракт Brain

1. Начни с маршрута `start_task.py` и прочитай README и единственный действующий `plan.md` задачи. Сверь постановку, выбранные решения, границы записи и критерии готовности.
2. Следуй действующему оркестратору проекта. Для разрешённого делегирования найди через `python3 rules/scripts/skill_index.py --search agent-orchestrator-evidence-first --format block` точное имя и прочитай напечатанный канонический `SKILL.md`. Этот скил дополняет его, а не меняет гейты, владельцев файлов или независимую приёмку.
3. В 1С исполнение ведёт develop. Используй этот текст только для управления фронтом, если это совместимо с утверждённым планом.
4. Действующая авторизация определяет создание веток, worktree, PR и слияний. Этот скил сам их не разрешает и не требует. Используй уже выбранную схему интеграции; при последовательном исполнении фронт обрабатывается одним агентом.

## Цикл исполнения

1. **Построй фронт.** Для каждой части укажи блокирующие зависимости и критерий приёмки. Исследование оставляй отдельной работой только когда оно действительно нужно. Ссылки на код и заметки передавай вместо копий постановки.
2. **Подготовь исполнителя.** При разрешённом делегировании выдай ему часть плана, пути контекста, разрешённые файлы, базовую версию и требуемые доказательства. Исследователь сохраняет только нужные выводы в законном месте задачи; временные материалы Brain идут в `D:/Brain/temp`.
3. **Проверь базу.** Если проект применяет отдельные worktree, проверь исходную версию перед изменениями. Расхождение базы разбери по правилам оркестратора; разрушительный reset из этого скила не следует.
4. **Сделай сквозную часть.** Прочитай [mp-tdd](../mp-tdd/SKILL.md) и применяй red → green там, где выбран подходящий тестовый контур. Не вводи тест ради каждой обратимой правки.
5. **Прими результат.** Отчёт исполнителя служит указателем. Приёмщик читает фактический diff и проверяет критерии и результаты команд. При отдельной ветке проверяют совместимость с текущим интеграционным состоянием до принятия. Интеграцию выполняет уполномоченный участник действующего процесса.
6. **Пересчитай фронт.** Разблокируй только части с принятой зависимостью. Ошибку проверки верни исполнителю с наблюдаемым симптомом. Параллельно запускай лишь независимые разрешённые части без пересечения защищённых файлов.

Пример: A задаёт интерфейс, B и C используют его, D связывает результаты. Сначала готова A. После её приёмки готовы B и C. D готова только после приёмки обеих. Завершившийся агент не равен принятой задаче.

```text
A принята → B принята ─┐
           C принята ─┴→ D → общее ревью
```

## Общее ревью и завершение

1. После приёмки всех частей просмотри совокупное изменение против постановки, включая связи между частями.
2. Для общего кода выполни `python3 rules/scripts/skill_index.py --search ao-code-review-and-quality --format block`. Найди блок с точным именем `ao-code-review-and-quality` и прочитай указанный канонический `SKILL.md`: это другой источник, а не соседний каталог этого форка. При неполном поиске используй `--block ao-code-review-and-quality`. Если точного имени нет, явно укажи неразрешённую зависимость; похожий результат поиска не заменяет скил.
3. Для 1С используй review-1c по пути, который показывает маршрут задачи или индекс. Общее ревью не заменяет его BSL-диагностику и предметные проверки.
4. Исправления ревью проходят тот же контракт приёмки. Затем обнови действующий план доказательствами и сообщи оставшиеся ограничения. Закрытие задачи выполни штатным процессом Brain, когда выполнены критерии результата.
5. Если ранее отдельно разрешены PR или временные worktree, завершай их по этому разрешению. Удаляй только созданные для этой задачи и уже не нужные ресурсы после проверки состояния.

Готово, когда весь принятый объём реализован, проверен независимо по контракту проекта и отражён в единственном плане. Ожидающие разрешения внешние действия показываются отдельно.
