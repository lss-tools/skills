# Предметная модель

Активно уточняй модель во время обсуждения: проверяй слова, отношения и крайние сценарии. Простое чтение существующего словаря не требует этого скила.

## Метод

1. Прочитай предметные термины и факты из материалов текущей задачи. Если тема затрагивает несколько контекстов, выясни область действия каждого понятия. Одинаковое слово может обозначать разные сущности в разных контекстах.
2. Сравни речь владельца с принятыми определениями. Противоречие покажи сразу: «Здесь отмена определена для всего заказа; сейчас речь идёт об одной строке». Сначала проверь, не объясняется ли разница контекстом.
3. Для расплывчатого слова предложи точный канонический термин. Например: «Под учётной записью понимаем пользователя системы или договор клиента?» Задавай вопросы по одному; факты из кода устанавливай самостоятельно.
4. Проверь отношения конкретными случаями. Можно ли вернуть часть строки? Может ли платёж относиться к двум заказам? Что происходит после удаления связанного объекта? Ищи случаи, которые различают понятия, а не просто подтверждают удобный пример.
5. Сопоставь сказанное с кодом. Различай текущее поведение и желаемую модель: расхождение само по себе не доказывает ошибку ни одной стороны. Покажи источник и влияние расхождения.
6. Как только термин определён, зафиксируй его в соответствующей части README «Постановка». Не откладывай запись до конца интервью. Формат и пример: [GLOSSARY-FORMAT.md](GLOSSARY-FORMAT.md).
7. Когда выбор меняет модель, запиши его в README «Решения». Для значимых архитектурных выборов используй три критерия из [ADR-FORMAT.md](ADR-FORMAT.md). Не превращай каждое определение в отдельное решение.

```text
слово → контекст → конкретный сценарий → проверка кодом
                                      ↓
                         определение или открытое противоречие
```

В Brain выходом служат существующие документы задачи. Не создавай автоматически `GLOSSARY.md`, карту словарей или каталог ADR. Существующий канон терминов читается как источник; предложение изменить канон передаётся в его штатный процесс.

## Готовность

1. Существенные понятия определены коротко и без деталей реализации; синонимы не маскируют разные сущности.
2. Для спорных отношений проверены различающие сценарии, включая исключения.
3. Области действия терминов и связи контекстов понятны. Противоречия с кодом разрешены или явно оставлены открытыми.
4. Определения и решения записаны при их принятии, без второго словаря. Стадийный анализ и архитектура 1С сохраняют свои требования.
