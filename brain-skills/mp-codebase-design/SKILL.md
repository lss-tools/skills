# Глубокие модули

Проектируй модуль, который скрывает значимое поведение за небольшим интерфейсом. Его ценность: вызывающему коду нужно знать меньше, а изменения и проверки сосредоточены в одном месте.

## Единый словарь

1. **Модуль:** единица с интерфейсом и реализацией. Масштаб не задан: функция, класс, пакет или сквозная часть системы.
2. **Интерфейс:** всё, что вызывающий код должен знать для правильного использования. Сюда входят параметры, инварианты, порядок действий, ошибки, настройка и существенные ограничения производительности.
3. **Реализация:** внутреннее устройство модуля. Это содержание, тогда как адаптер описывает роль.
4. **Глубина:** сколько поведения доступно на единицу сложности интерфейса. Её не измеряют отношением числа строк.
5. **Точка подмены (seam):** место, где поведение можно заменить, не меняя вызывающий код. Отдельно решай, где она находится и какая реализация за ней скрыта. Не смешивай её с границей предметного контекста.
6. **Адаптер:** конкретная реализация контракта в точке подмены. Сетевой адаптер может быть большим внутри; тестовый адаптер может иметь другой внутренний объём.
7. **Отдача интерфейса (leverage):** сколько возможностей получает вызывающий код за изучение контракта.
8. **Локальность:** сколько знания, правок, дефектов и проверок сосредоточено внутри модуля вместо распределения по вызывающему коду.

Используй эти термины последовательно. Не своди интерфейс к ключевому слову языка или списку публичных методов.

```text
много вызывающего кода → небольшой интерфейс
                        ┌────────────────────────┐
                        │ скрытое поведение       │
                        │ и внутренние адаптеры   │
                        └────────────────────────┘
```

## Работа с выбранным модулем

1. Прочитай реализацию и реальные места вызова. Опиши, что вызывающий код уже обязан знать и где повторяет внутренние правила.
2. Проверь глубину. Можно ли уменьшить число операций, упростить параметры и спрятать существенную сложность? Небольшая реализация под большим интерфейсом обычно лишь пересылает работу дальше.
3. Выполни мысленный тест удаления. Если при удалении модуля сложность исчезает, он был лишним посредником. Если сложность возвращается во множество вызовов, модуль выполнял полезную работу.
4. Выбери точку подмены. Глубокий модуль может содержать приватные точки подмены для своих проверок. Не делай их частью внешнего интерфейса только ради тестов.
5. Классифицируй зависимости по [DEEPENING.md](DEEPENING.md). Это определяет, где нужен адаптер и какие проверки возможны. Одна реализация без реальной потребности в замене означает гипотетическую точку подмены.
6. Сформулируй контракт и пример использования. Передавай изменяемые зависимости явно. По возможности возвращай результат вычисления, чтобы проверять его без скрытого изменения внешнего состояния.
7. Если первый вариант вызывает сомнения, сравни существенно разные интерфейсы по [DESIGN-IT-TWICE.md](DESIGN-IT-TWICE.md). Не называй переименование аргумента отдельным дизайном.
8. Запиши выбранный контракт, компромисс и проверяемое внешнее поведение в README «Решения». Исполнение и его проверки помещаются в единственный plan.md, если это входит в поручение.

```typescript
// Зависимость видна и заменяема.
function processOrder(order, paymentGateway) {}
// Создание StripeGateway внутри processOrder скрывает обязательную зависимость.

// Результат можно проверить через интерфейс.
function calculateDiscount(cart): Discount {}
// applyDiscount(cart): void скрывает результат в изменении cart.
```

Это приёмы проектирования, а не запрет необходимых побочных эффектов. У интерфейса модуля одна согласованная внешняя поверхность; приватных точек подмены может быть несколько. Вызывающий код и проверки проходят через один внешний контракт.

## Готовность

1. Понятно, что интерфейс обещает и какую сложность скрывает реализация.
2. Потребности существующих вызовов покрыты; глубина обоснована поведением, а не длиной кода.
3. Для каждой важной зависимости выбран реалистичный способ проверки. Новая абстракция оправдана действительной вариативностью.
4. Выбор улучшает отдачу интерфейса и локальность либо явно называет компромисс. Отдельный HTML-отчёт не требуется; стадия архитектуры 1С не заменяется.
