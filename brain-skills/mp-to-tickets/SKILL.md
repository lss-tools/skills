# Сквозные блоки плана

Разбей работу на узкие, но завершённые части поведения. Каждый блок должен показывать работающий результат и явно называть только действительные предпосылки.

## Метод

1. Прочитай принятую постановку и решения README. Если указан дополнительный источник, прочитай относящееся к задаче содержимое и обсуждение. Открытые решения не превращай в молчаливые требования.
2. Изучи релевантный код, если ещё не знаешь его устройство. Используй принятые предметные термины. Найди подготовительную реструктуризацию, которая действительно нужна, чтобы изменение можно было сделать безопасно и просто.
3. Набросай сквозные блоки. Обычный блок проходит через нужные ему слои: хранение, операции, интерфейс пользователя и проверку. Завершённый блок демонстрируется или проверяется отдельно; он помещается в один свежий рабочий контекст. Не дели автоматически на «вся схема», «весь сервер», «весь интерфейс».
4. Для каждого блока назови предшественников, без которых его нельзя начать. Последовательность ради удобства не равна блокировке. Подготовительное изменение ставь первым лишь при реальной необходимости и с отдельной проверкой сохранения поведения.
5. Покажи нумерованный черновик: название, что получает пользователь, что блокирует работу и как проверить результат. Если согласование ещё требуется, уточняй по одному: размер блоков, истинность зависимостей, необходимость разделить или объединить. При принятом автономном поручении продолжай в его границах без повторного разрешения.
6. Запиши результат в единственный plan.md задачи, в порядке зависимостей. Сохрани существующую структуру плана и доказательства исполненных пунктов; не заводи отдельные файлы тикетов и второй список статусов.

```text
принятая постановка → сквозные результаты → реальные блокировки
                                         ↓
                         plan.md → доступный фронт исполнения
```

## Форма блока

```markdown
### Б-n. Короткое название результата

**Результат:** наблюдаемое поведение, которое появится целиком.
**Зависит от:** Б-x, потому что ...; либо «нет».
**Проверка:** конкретные действия и ожидаемые результаты.
**Готово, когда:** критерии, позволяющие принять этот блок независимо.
```

Называй устойчивые контракты и ограничения. Для практического исполнения можно указывать проверенные пути, но путь или строка не должны быть единственным определением результата. Содержательный фрагмент прототипа допустим, если он точнее фиксирует решение; сохрани только значимую часть и её происхождение.

## Исключение: широкая механическая правка

Если одно переименование или изменение общего типа ломает множество вызовов сразу, независимые сквозные блоки могут быть невозможны. Используй расширение и последующее сужение:

1. Добавь новую форму рядом со старой, сохранив работоспособность.
2. Переводи потребителей партиями по области влияния. Каждая партия зависит от расширения и сохраняет проверки за счёт старой формы.
3. Удали старую форму только после всех партий и проверки отсутствия потребителей.

Если партии нельзя проверить самостоятельно, явно укажи общую интеграционную область и финальный блок интеграции, заблокированный всеми партиями. Не обещай успешные проверки каждого промежуточного состояния. Сам план не создаёт ветки и не разрешает запуск агентов.

## Готовность

1. Каждый обычный блок даёт завершённый проверяемый результат, а исключение для механической правки обосновано.
2. Граф не содержит циклов или вымышленных блокировок. Доступный фронт: блоки, все предшественники которых завершены.
3. Подготовительные действия имеют доказуемую необходимость, а каждый критерий приёмки связан с постановкой.
4. В задаче один plan.md. Для 1С результат встраивается в architect; этот скил не заменяет проектирование или develop.
