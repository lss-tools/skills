# Синтез постановки

Собери уже известное в ясный контракт. Этот скил не начинает новое интервью и не принимает решения вместо владельца.

## Метод

1. Прочитай README и нужные материалы обсуждения. Если текущее устройство ещё неизвестно, исследуй релевантный код. Используй принятые предметные термины и соблюдай действующие решения. Сохрани установленные факты research с их источниками.
2. Найди внешнюю точку проверки поведения. Предпочитай существующий интерфейс наиболее высокого подходящего уровня: проверяющий должен видеть результат пользователя, а не частные детали реализации. Чем меньше точек требуется для доказательства поведения, тем проще контракт; идеал одной точки не отменяет самостоятельные внешние гарантии.
3. Если нужна новая точка подмены, прочитай [mp-codebase-design](../mp-codebase-design/SKILL.md). Отдели согласованное решение о проверке от новой рекомендации. Не выдумывай согласие: оставь требующий выбора вариант в «Неизвестном». Если владелец уже разрешил соответствующий выбор, запиши основание и продолжай.
4. Заполни README «Постановка» по форме ниже. Объём сценариев определяется полнотой поведения, а не требованием длинного списка.
5. Перенеси существенные технические выборы в «Решения», сохранив их основание. Неразрешённые вопросы запиши в «Неизвестное». Не публикуй issue и не объявляй задачу готовой через внешнюю метку.

```text
обсуждение + факты + решения → роли и сценарии
                            → наблюдаемые проверки
                            → постановка с явными пробелами
```

## Состав постановки

1. **Проблема:** что затрудняет работу пользователя сейчас, в каком контексте и с каким последствием.
2. **Результат:** что сможет сделать пользователь после изменения. Описывай его поведение и результат.
3. **Роли и сценарии:** для каждого существенного участника укажи действие, цель и условия. Допустим формат: «Как бухгалтер, хочу видеть причину отказа проведения, чтобы исправить документ». Включи основные сценарии, ошибки, исключения и права, когда они влияют на результат.
4. **Проверки:** наблюдаемое поведение, проверяемые модули или операции, выбранные внешние точки проверки и существующие примеры подходящих проверок. Проверки реализации не заменяют результат для пользователя.
5. **Границы:** что сознательно исключено из этого изменения.
6. **Примечания:** существенные ограничения или ссылки, которые не помещаются в предыдущие части. Не дублируй здесь принятые решения.

Технические решения могут затрагивать модули, их интерфейсы, схему данных, протоколы и взаимодействия. Описывай устойчивый контракт, а не предполагаемый список редактируемых строк. Ссылки на код служат доказательством текущего состояния. Они не заменяют требование и не становятся вечным техническим маршрутом.

Если прототип выразил решение точнее текста, можно сохранить минимальный фрагмент схемы, автомата состояний или структуры типа в соответствующем решении. Укажи происхождение из прототипа и убери демонстрационный код, который не несёт решения.

## Готовность

1. Другой исполнитель понимает проблему, участников, желаемый результат, исключения и пределы изменения.
2. У каждого существенного сценария есть способ проверить результат через внешнее поведение.
3. Факты, принятые решения, рекомендации и неизвестное различимы; ничего не согласовано задним числом.
4. README остаётся единственной постановкой. Для 1С синтез дополняет материалы действующей стадии analyze, сохраняя её требования.
