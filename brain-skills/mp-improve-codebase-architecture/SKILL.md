# Поиск возможностей углубить модули

Цель: уменьшить знания, которые нужны вызывающему коду, и собрать изменение, ошибки и проверку в одном месте.
Сначала прочитай [mp-codebase-design](../mp-codebase-design/SKILL.md). Используй его определения: модуль, интерфейс, реализация, глубина, точка подмены (seam), адаптер, отдача интерфейса (leverage), локальность. Предметные имена бери из канонических фактов и документов задачи Brain. Принятые решения читай до поиска кандидатов.

## 1. Выбрать область

1. Используй указанный пользователем модуль, подсистему или затруднение.
2. Если область не названа, прочитай достаточно истории `git log --oneline`, чтобы увидеть повторяющиеся изменения. Начни с этих мест. При рассеянных изменениях расширь поиск.
3. Ограничь обзор ожидаемой пользой текущей задачи. Углубление окупается там, где снова придётся менять поведение.

Готово, когда названы область, причина её выбора и решения, которые ограничивают варианты.

## 2. Найти трение

Исследуй код сам или через исполнителя, если делегирование разрешено действующим процессом. Подтверждай наблюдения путями и вызовами:

1. Для одного понятия приходится переходить между многими мелкими модулями.
2. Интерфейс почти так же сложен, как реализация: модуль мелкий по глубине.
3. Чистые функции вынесены ради тестов, а ошибки живут в связях между вызовами: локальность потеряна.
4. Связанные знания протекают через точку подмены и вынуждают менять несколько вызывающих мест.
5. Важное поведение трудно проверить через действующий интерфейс.

Проведи мысленный тест удаления. Если сложность исчезнет, модуль лишь передаёт вызовы. Если она распределится по вызывающим местам, модуль её скрывал. Не путай эти результаты.

## 3. Сравнить кандидатов

Для каждого кандидата запиши:

1. Файлы и модули с навигационными ссылками.
2. Наблюдаемое трение и подтверждающий сценарий.
3. Какое знание уйдёт внутрь реализации при углублении.
4. Выигрыш в локальности, отдаче и проверке через интерфейс.
5. Схему до/после и силу рекомендации: «сильная», «стоит исследовать», «предположение».
6. Конфликт с принятым решением, только если реальное трение оправдывает пересмотр.

Сначала сравни направления, затем детализируй интерфейс выбранного. Например: до `ПриёмЗаказа → Проверка → Хранилище → РасчётЦены`, причём вызывающий код знает порядок; после один модуль приёма заказа скрывает порядок за малым интерфейсом. Выигрыш: один сценарий проверяет весь контракт; знание цены остаётся внутри.

Результат помести в принятое место задачи. Для нескольких сложных кандидатов используй [формат визуализации](references/report.md), если визуализация помогает выбору. HTML необязателен; временный экспорт Brain хранится в `D:/Brain/temp`.

Заверши общей рекомендацией и её причиной. Если выбор уже разрешён текущим поручением, продолжай в его рамках. Иначе задай один вопрос о кандидате.

## 4. Исследовать выбранное направление

Прочитай [mp-grilling](../mp-grilling/SKILL.md) для дерева зависимых решений и [mp-domain-modeling](../mp-domain-modeling/SKILL.md) при уточнении предметных терминов. Задавай вопросы по одному; не переоткрывай принятый выбор без новых фактов.

Уточни ограничения, зависимости, что скрывает модуль, где находится точка подмены и какие тесты сохранятся. Для разных интерфейсов используй метод сравнения из mp-codebase-design. Новые термины и решения вноси в законные документы задачи; отдельный `GLOSSARY.md` автоматически не создавай. Существенный отказ сохрани как решение с полями «Отвергли» и «Пересмотреть если», чтобы следующий обзор не предлагал то же самое без причины.

Готово, когда выбранное направление имеет проверяемую причину, известные ограничения и следующий шаг. Для стадии архитектуры 1С результат передаётся в действующий architect.
